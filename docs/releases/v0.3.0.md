# oshost v0.3.0

Compared with `v0.2.0` (`b400a1d`). Includes the notification and webhook improvements previously published under the build-only tag, plus the new webhook editors and granular JSON transfers.

## Webhook doors

- Support generic HTTP/HTTPS webhooks with configurable methods, headers, raw request bodies and success-response handling. eWeLink and Shelly Cloud are editable presets of the same webhook integration.
- Edit headers and query parameters as key/value rows. The + button becomes available only when the existing rows are complete. Duplicate header names are rejected case-insensitively; repeated query parameters and URL encoding are preserved.
- Put the eWeLink code and Shelly query credentials in the query editor. Pasting a complete URL separates its query parameters into rows.
- Automatically convert existing eWeLink/Shelly door configurations and old portable backups, preserving IDs, metadata and request behavior. Credentials remain encrypted in the database. Device requests are not retried automatically and do not follow redirects.

## Granular JSON transfers

- Owners/admins can download and upload **Doors JSON** or **Access codes JSON** from the corresponding list page for the selected structure. These controls and APIs cannot be delegated through collaborator permissions.
- Door files include configurations, photos, credentials and test history. Access-code files include guest tokens, permissions, consumption, breakfast history, actions, counters and activity. They cover the entire structure, including disabled doors and guest/staff/revoked codes; current calendar and search filters do not restrict the file.
- Append mode adds missing IDs and skips existing records. Override mode replaces the entire selected list and requires a specific warning, acknowledgement and typed confirmation.
- Replacing doors deletes omitted doors and their access-code permissions while retaining codes and usage for remaining doors. Replacing access codes removes the current code list and related history, then restores the file's saved records and history. **Older files can reactivate revoked guest links or reset consumed access.** Keep a backup before replacing a list.
- Imports validate references and device settings, re-encrypt credentials with the destination key, and commit atomically. Other structures and user accounts are unchanged. Import doors first when transferring codes to another installation. In-flight and unresolved device work blocks replacement. Files contain working credentials or guest links and must be kept private; the import limit is 32 MB.

## Notifications

- Show key icons for code changes, warning icons for errors and primary-door thumbnails for new successful door-use events when a photo is available. Older events without a door reference fall back to an icon.
- Clicking a history entry, in-app toast or browser push notification marks it read and opens the related code or door. Invalid attempts have no destination. Opening or scrolling history does not mark entries read; **Mark all as read** remains available. Read entries are gray, with read status synchronized across the reader's devices.
- Load history in pages of 20 and append older entries automatically while scrolling.
- Add a per-structure notification-count limit alongside retention time. The default is **1,000 entries**, configurable from 1 to 100,000. The oldest events, context, read receipts and queued pushes are deleted when either limit is exceeded; lifetime usage statistics remain.

## Upgrade and API notes

- Back up the database and runtime encryption keys before upgrading. Schema version 8 adds the count-retention setting. **Existing history is capped at 1,000 entries per structure by default**, so older notifications may be removed during upgrade even when still inside the configured retention period. Inactive structures retain their archived history until reactivated.
- `GET /events` now always returns `{events,nextCursor}`, with a default page size of 20. Consumers expecting the old bare array must update. Event responses include presentation metadata and optional door references.
- Door reads now report `integration:"webhook"` for connected doors. Legacy provider inputs are normalized for compatibility; webhook storage/API settings still use a complete URL and JSON-encoded headers.
- Granular transfer files have distinct version-1 formats (`oshost-doors` and `oshost-codes`). The existing whole-workspace JSON backup format remains available and unchanged in purpose.

## Validation

- TypeScript/Svelte checks and production builds for both apps.
- 125 automated tests, including owner-only authorization, atomic rollback, whole-list replacement, pending-device safeguards, cross-installation transfer and URL/header encoding.
- Browser flows covering pair-editor controls, file download and preview, append/replacement confirmations, collaborator restrictions, door setup, guest breakfast, PWA scopes, offline drafts and mobile layout.
